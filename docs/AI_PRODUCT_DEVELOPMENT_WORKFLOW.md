# AI 产品开发精简工作流

确认日期：2026-09-03  
适用对象：使用 ChatGPT 与 Codex 完成产品设计、开发和发布的个人或小团队。

本文保存 Ta-da! 项目复盘后已确认的工作方式，作为后续项目与迭代的 SOP。Ta-da! 已于 2026-09-03 依据 D-050 启用精简协作方式；当前执行范围、版本与未完成项以 STATUS.md 为准。本文不构成开发、创建云服务或发布的自动授权。

## 一、先记住四个原则

1. **Git + 远端仓库。** 代码有版本、成果可追溯；保存文件不等于提交，提交也不等于已同步 GitHub。
2. **AI 先自测。** AI 先证明功能可用，再交给用户。用户不是第一轮测试员。
3. **用户亲自验证。** AI 检查通过不能代替用户对真实流程、视觉、文案和体验的确认。
4. **单一权威状态与统一版本。** 只有一个 main、一份当前状态、一个统一验收入口；公网发布另有明确版本。

## 二、只保留两个长期任务

ChatGPT 负责最初的产品发散与项目启动包：用户是谁、解决什么问题、首版做什么、主流程、设计参考及暂不做的内容。进入 Codex 后，持续的产品决策集中在 05，不再让 ChatGPT 与多个编码任务同时维护不同版本的需求。

| 任务 | 负责什么 | 不负责什么 |
|---|---|---|
| **05 产品与设计决策** | 需求讨论、流程、信息结构、文案、视觉参考、范围取舍，形成已确认输入 | 不直接改业务代码，不承诺某个版本已上线 |
| **00 总控与版本状态** | 技术计划、任务边界、共享决定落盘、版本状态、复核、集成、自测和发布安排 | 不与模块任务同时写同一范围，不把聊天结论当唯一依据 |
| 临时编码任务 | 在明确范围内交付一个可验证结果，包括实现与 AI 自测 | 不自行扩大范围、改共享契约或发布公网 |
| 临时独立 QA 任务 | 在重大版本或核心流程变更时提供独立检查 | 不作为长期固定的 90 任务，也不自动获得修复权限 |

普通功能的集成检查由 00 执行。只有风险值得独立检查时才开临时 QA；不设长期 90，不代表取消 QA。任务名称代表职责，不代表系统会自动同步代码或形成上下级控制。

## 三、项目开始时，一次把环境搭好

正式开发前，由 00 建立并验证以下基础：

- 初始化 Git 与 GitHub 远端，确定唯一主线 main 和可回退的初始版本。
- 建立 AGENTS.md、STATUS.md、DECISIONS.md，明确写入权限、当前状态与已确认决定。
- 配好类型检查、测试、构建，以及实际操作页面所需的浏览器工具；必要时补 Computer Use。
- 跑通最小页面、统一预览与部署基础，明确预览来自哪个目录、哪次提交。
- 区分本地草稿、演示数据和正式数据，避免把临时入口或样例能力说成正式发布能力。

环境准备完成后，每个功能都使用下面同一个循环，不再重新发明流程。

## 四、每个功能只走四步

```text
05 定义 → 00 计划 → 临时实现 + AI 自测 + 00 集成 → 用户验收
   ↑          ↑                    ↑                    │
   └──────────┴──── 按问题类型返回，不必整轮重做 ────────┘

用户验收通过 → 已验收；批准发布并完成部署检查 → 已发布
```

| 步骤 | 谁负责 | 必须得到的结果 |
|---|---|---|
| **1. 定义** | 05 与用户 | 用户目标、本次范围、不做什么、关键流程、必要的视觉与文案参考、验收标准 |
| **2. 计划** | 00 | 快速或完整模式、技术方案、允许改动范围、依赖及公共接口、验证方法、集成与回退安排 |
| **3. 实现** | 临时编码任务；00 复核集成 | 在授权范围实现、自测并交付提交；00 核对依赖和冲突，逐个集成 main，刷新统一预览并复验 |
| **4. 验收** | AI 先检查，用户后体验 | 用户在同一个集成版本上走完相关流程，确认视觉、操作和文案；未通过的反馈回到对应步骤 |

这四步没有省略原来的五阶段：环境搭建只在项目开始完成；产品设计对应“定义”，技术设计对应“计划”，实现与自测对应“实现”，人工验证对应“验收”。

只冻结本次要实现的部分，不要求产品从此不能变化。新想法进入后续迭代；如果会改变当前任务的范围或接口，先回 05 / 00 更新任务卡，再恢复实现。

## 五、只分快速与完整两种模式

**快速模式**适用于简单、低风险、影响范围清楚、容易回滚的修改。定义和计划可以很短，放在一张任务卡中，但不省略自测、版本记录、统一预览和用户验证。

**完整模式**适用于核心流程、跨模块、复杂交互、公共数据、高成本或难回滚的变更。先确认产品流程和必要视觉，再由 00 明确公共契约、依赖、错误降级与集成顺序；必要时开临时独立 QA。拿不准时默认完整模式。

00 可以直接处理很小的修改，但必须同时满足：易回滚、不改变公共接口或主流程、没有并行冲突、工作区干净。完成后仍须自测、形成提交并刷新统一预览。否则使用临时编码任务；不能以“只是小改动”为由覆盖他人未保存成果。

上述提交要求属于实施环节；讨论、保存方案或整理状态不构成提交代码的自动授权。

## 六、临时任务、分支和集成怎么配合

正常功能遵循：**一个明确结果 → 一个临时编码任务 → 一个 Worktree（独立工作目录）→ 一个分支。** 一个活跃分支同一时间只由一个编码任务写入。00 负责读、复核和集成，不与模块共同写代码。

默认串行。确需并行时，先冻结接口和互不重叠的改动范围，确认每个结果可独立检查；最多同时运行 3 个编码 Worktree。共享文件不能靠“大家小心一点”避免冲突，必须指定唯一写入者。集成始终一个接一个。

新任务和 Worktree 需要用户明确授权。任务卡列出基线提交与前置依赖，不能依赖另一个工作目录中尚未提交的文件。

模块交付后的处理顺序：

1. 编码任务完成自测，交回提交号、范围、证据和风险，然后冻结等待，不继续追加未交接修改。
2. 00 核对结果与任务卡，检查公共依赖、现有修改和冲突，再将该结果集成 main。
3. 00 运行集成检查，从对应版本刷新统一预览，确认用户看到的确实是本次集成结果。
4. 集成验证完成，且没有未保存、未提交或尚未接收的成果后，再安排归档和安全清理；不能在“模块已交付”时立即删除工作目录。

归档对话、删除 Worktree 和删除分支不是同一件事。清理前必须确认成果可恢复，并遵守原有清理授权；不使用强制删除掩盖脏工作区。

## 七、先自测，再邀请用户验收

AI 根据改动风险执行适用检查，并如实记录未执行项及原因：

- 类型检查、相关自动化测试、生产构建。
- 真实浏览器点击、输入、返回、保存和恢复，不能只看页面截图或服务返回成功。
- 控制台错误、资源请求失败、链接和按钮可用性。
- 移动端尺寸与触控；Ta-da! 以 390×844 为主，并覆盖 360–430px 宽度。
- 错误、空状态、权限拒绝、读取失败及其他相关降级；有动效时检查 reduced-motion。
- 集成后的前后步骤与相关分支，确认没有“模块单独正常，主流程却不正常”。

缺少浏览器或操作工具时，先补齐环境，不能把未验证页面直接交给用户，也不能写成检查已通过。用户主要确认“是不是想要的产品”和实际使用感受，不负责审查类型、提交或合并冲突。

**三个地址必须分清：**

| 入口 | 能证明什么 | 谁负责 |
|---|---|---|
| 模块预览 | 某个任务的局部实现，不保证周边模块最新 | 临时编码任务 |
| 统一预览 | main 上一个明确集成版本的完整体验，是用户验收入口 | 00 |
| 公网 | 已获发布批准、部署完成且检查过的版本 | 00 管理发布状态 |

统一预览自动更新不等于公网自动发布。公网只部署已批准版本；部署配置应支持这一边界，不能让未经批准的 main 更新绕过发布确认。公网可以暂时落后于统一预览，但必须显示清楚各自版本，不能都称为“最新版”。

验收邀请发出后，说明对应版本。若中途又更新了版本，00 必须告知变化并补做相关检查，不能沿用上一版本的验收结论。

## 八、反馈、状态和文档保持简单

反馈按原因回到正确位置：产品逻辑、视觉或文案含义回 **05**；技术方案、公共数据或跨模块问题回 **00 重新计划**；代码 Bug 回 **实现 / 修复任务**；无法测试或工具失效则 **补环境**。小范围问题只重做受影响环节，不为每条反馈重新开完整流程。

用户只需要看六个状态：

| 状态 | 含义 |
|---|---|
| 待定义 | 用户目标、范围或验收标准尚未明确 |
| 可开发 | 本次产品输入与技术计划已就绪，待获授权后启动 |
| 开发中 | 正在实现、自测、修复或集成；模块提交完成仍可能处于此状态 |
| 待验收 | 已集成，统一预览已刷新，AI 检查通过，等待用户体验 |
| 已验收 | 用户明确通过当前版本，尚不代表公网已更新 |
| 已发布 | 已批准版本部署完成，并通过公网检查 |

阻塞原因写在当前状态旁，不另造一套状态。提交、分支、检查结果和预览来源保留为内部证据，用户不需要操作 Git。只有 00 更新权威状态，不能根据模块的一句“完成了”跳到“已发布”。

最小治理文件只要求三个：AGENTS.md 记录职责和权限，STATUS.md 记录当前状态、版本及下一步，DECISIONS.md 记录已确认决定及其变化。共享决定由 00 写入并提交，聊天不是唯一依据。

已有产品、流程、接口和设计契约继续保留，不为追求精简而删除。小功能只用一张合并产品、技术和验收信息的任务卡；复杂功能才增加独立文档，避免相同规范复制到多处。

## 九、四张可直接复用的交接卡

### 版本身份卡

```text

公网：地址 + 部署提交 + 检查时间（未发布则写未发布）
已包含 / 未包含：
检查结果与风险：
下一步与负责人：
```
